# 같은 Wi-Fi에서 노트북 음악방 공유

별도 서버 임대 없이 Node 서버를 실행한 컴퓨터의 내부 IP와 포트를 사용합니다. 같은 SSID라도 회사 네트워크에서 단말 간 접근이 차단되어 있으면 접속할 수 없습니다. 공유기 포트포워딩·외부 터널·자동 방화벽 변경은 사용하지 않습니다.

## 접속 페이지

| 경로 | 용도 | 인증 |
|---|---|---|
| `/queue` | 현재 곡 상태·전체 대기열, 5초마다 자동 갱신 | LAN 공유가 켜져 있으면 키 불필요 |
| `/` | 기존 관리자 화면·신청·재생 제어 | 기존 adminToken |
| `/player` | 브라우저를 실제 재생기로 사용 | 기존 playerToken / 관리자 발급 임시 키 |

플리 페이지를 열기만 하면 재생에 영향을 주지 않습니다. `lan.requests.enabled`를 켜면 곡명 검색·후보 선택·영상/목록 링크 신청도 가능합니다. 관리자 권한이나 재생기 임대는 주지 않습니다. Google Chat 비공개 신청창도 계속 사용할 수 있습니다. 관리자 권한이 필요한 사람만 관리 키를 사용합니다. 관리자 키를 URL에 넣지 않습니다.

공유 API는 현재 곡과 대기곡의 제목·영상 ID·상태, 일시정지 여부만 반환합니다. 신청자·스페이스·세션 ID·이력·진단 정보·연결 키를 반환하지 않습니다. 실제 재생 확인이 없는 곡은 재생 중으로 표시하지 않습니다. 네트워크 연결이 끊기면 마지막 표시 정보임을 알립니다.

## 설정

기본 설정은 loopback + 공유 꺼짐입니다. 의도적으로 LAN을 열 때만 다음 두 항목을 변경합니다.

```json
{
  "host": "0.0.0.0",
  "lan": { "enabled": true }
}
```

`0.0.0.0`은 접속 URL이 아닌 수신 설정입니다. 동료는 `http://컴퓨터의-내부-IP:8787/queue`로 접속합니다. 컴퓨터 자신은 기존 `http://127.0.0.1:8787/` 주소도 사용할 수 있습니다. LAN 모드는 loopback 및 사설 IPv4 출발지만 허용하며, Host 값은 요청이 도착한 서버의 IP/포트와 일치해야 합니다. 임의 DNS 호스트·X-Forwarded-For·X-Forwarded-Host로 허용 범위를 넓히지 않습니다. 역방향 프록시나 임의 도메인 이름을 위한 설정은 아닙니다.

[Node 서버의 host 수신 설정](https://nodejs.org/api/net.html#serverlisten)은 네트워크 노출 범위를 바꿉니다. 이 구현은 모든 IPv4 인터페이스에서 수신하되 사설 주소/Host 검사를 추가합니다. HTTP 자체에는 암호화가 없으므로 신뢰하는 사내 네트워크에서 사용하며 인터넷으로 포트를 공개하지 않습니다. API 인증·동일 출처 검사·CORS 미허용·IP별 요청 제한은 유지합니다.

## 다른 기기에서 접속이 안 될 때

1. 서버 컴퓨터가 켜져 있고 서버 프로세스가 실행 중인지 확인합니다. 컴퓨터가 잠자기에 들어가거나 덮개를 닫으면 사용할 수 없을 수 있습니다.
2. 접속 기기도 같은 회사 Wi-Fi를 사용하고 있는지 확인합니다. 휴대폰 셀룰러 연결에서는 내부 IP에 접속할 수 없습니다.
3. Mac Wi-Fi 세부사항에서 현재 IP가 공유한 주소와 같은지 확인합니다. DHCP 때문에 재연결 후 IP가 바뀔 수 있습니다. [Apple의 IP 확인 안내](https://support.apple.com/guide/mac-help/mh11935/mac)를 참고합니다.
4. 해당 포트의 수신 연결이 차단된 경우 OS/회사 보안 정책을 담당자와 확인합니다. 프로그램이 방화벽이나 네트워크 보안 설정을 자동으로 바꾸지는 않습니다. 단말 격리·게스트 Wi-Fi 정책이면 회사 네트워크 담당자 확인이 필요합니다.

## 재시작과 복구

재시작 전 현재 `data/state.json`을 백업하고 기존 서버를 정상 종료합니다. 두 서버가 같은 대기열을 쓰지 않도록 잠금이 적용됩니다. TV 어댑터는 이미 재생 중인 곡을 관측해서 복구하며, 실제 영상이 저장된 현재 곡과 다르면 복구 대기 상태를 유지합니다. 확인 없이 TV에 재생·건너뛰기를 보내지 않습니다.

검색은 현재 LAN 배포에도 포함됩니다. 키 저장 여부와 별개로 `search.enabled`가 명시적으로 true인 경우에만 검색을 켭니다. 다시 이 컴퓨터에서만 접근하도록 닫으려면 `host`를 `127.0.0.1`, `lan.enabled`를 `false`로 바꾼 뒤 대기열 보존 절차로 재시작합니다.

## LAN 관리자 연결 보안

다른 기기의 관리자·재생기 연결은 HTTPS가 필수입니다. 일반 HTTP에서는 키가 맞아도 제어 API를 거부합니다. `/queue` 읽기와 localhost 관리 연결은 유지합니다. TLS가 켜져 있으면 HTTP 관리자 주소는 HTTPS 포트로 이동합니다.

`tls.enabled: true`, 별도 `tls.port`, 서버 인증서 `tls.certFile` 및 개인키 `tls.keyFile`을 설정합니다. 인증서는 접속 IP/이름을 SAN에 포함해야 하며, 이용 기기가 신뢰하는 인증서여야 합니다. 회사 발급 인증서를 권장합니다. 자체 서명 인증서는 운영자가 지문과 파일 전달 경로를 확인한 뒤 기기별로 수동 신뢰해야 합니다. 경고를 무시하고 키를 입력하지 마세요. 프로그램은 OS 인증서 신뢰를 자동 변경하지 않습니다. 개인키는 공유하지 않으며 data 폴더와 함께 Git에서 제외합니다. 인증서 만료·IP 변경 시 갱신이 필요합니다.

키는 URL에 넣지 않고, 이용을 마친 관리자는 **연결 해제**로 이 탭의 키를 지웁니다. 키 교체는 설정을 변경하고 대기열을 보존하여 재시작합니다. [점검 결과와 보안 경계](SECURITY.md)를 참고하세요.

## IP 변경에 대응하는 이름 주소

공유기의 DHCP 예약 권한이 없으면, 이미 Bonjour로 제공되는 컴퓨터의 실제 로컬 이름을 사용합니다. macOS에서는 `scutil --get LocalHostName`으로 확인한 이름에 `.local`을 붙입니다. 설정에 실제 이름을 명시해야 하며 임의 DNS 이름·와일드카드는 허용하지 않습니다.

```json
{ "host": "0.0.0.0", "port": 8787, "lan": { "enabled": true, "hostnames": ["your-laptop.local"] } }
```

같은 LAN의 Bonjour/mDNS 호환 기기에서 `http://your-laptop.local:8787/queue`를 엽니다. 서버가 IP를 고정하거나 DNS 서버를 새로 설치하지 않으며, OS 이름·공유기·방화벽 설정도 바꾸지 않습니다. 이름 주소와 포트는 IP가 바뀌어도 유지할 수 있지만, 컴퓨터 이름 변경/이름 충돌, VPN·네트워크의 멀티캐스트 차단 또는 클라이언트 mDNS 미지원에서는 사용할 수 없습니다. 이런 환경은 사내 DNS 또는 DHCP 예약을 담당자에게 요청해야 합니다. 숫자 IP 자체가 고정된 것은 아닙니다. [Apple 로컬 이름 설명](https://support.apple.com/guide/mac-help/mchlp2322/mac)을 참고하세요.

플리 하단에 이름 주소가 나타나며 HTTP에서 자동 클립보드가 제한되면 선택된 주소를 Ctrl+C/⌘C로 복사합니다. 이름 주소의 관리자 링크는 HTTP 페이지에서 키를 받지 않고 실제 수신 IP의 HTTPS 주소로 이동합니다. 기존 IP 인증서를 유지하므로 IP 변경 후 관리자 HTTPS 인증서는 갱신이 필요할 수 있습니다. 인증서 경고를 우회하지 마세요. 플리의 이름 주소와 테마 선택에는 관리자 키가 필요하지 않습니다.

## 맥북 이름과 독립적인 짧은 별칭 (macOS)

macOS의 기본 `/usr/bin/dns-sd -P`로 서버 전용 Bonjour 이름을 광고할 수 있습니다. 컴퓨터 이름·OS DNS·hosts 파일·공유기·방화벽을 변경하거나 OS 서비스를 설치하지 않습니다. 서버가 생성한 등록 프로세스만 관리하며 정상 종료 시 함께 종료합니다.

```json
{ "lan": { "enabled": true, "hostnames": ["office-jukebox.local"], "advertise": true, "networkInterface": "en0" } }
```

`networkInterface`는 실제 Wi-Fi 인터페이스를 지정합니다. 지정한 인터페이스의 사설 IPv4만 광고하며 인터넷 IP·loopback·다른 VPN 인터페이스는 광고하지 않습니다. 10초마다 주소 변경을 확인하고 등록을 갱신합니다. 서비스 주소는 `http://office-jukebox.local:8787/queue`입니다. 기존 Mac 이름을 `hostnames`의 두 번째 값으로 남겨 두면 이전 주소도 계속 허용합니다. macOS 이외의 서버에서는 이 광고 기능 대신 OS/사내 DNS에서 이름을 제공해야 합니다.

이 기능도 같은 LAN의 mDNS 지원이 필요합니다. 다른 기기의 이름 충돌이나 등록 실패 시 진단의 `bonjour` 상태를 확인하고 고유한 이름을 정합니다. `.local` 없는 단일 이름은 사내 DNS/검색 도메인 설정 없이는 보장할 수 없습니다. 서버 프로세스를 강제 종료하면 등록용 자식이 남을 수 있으므로 정상 종료를 사용하고, 문제가 있으면 운영자가 해당 프로젝트의 등록 프로세스를 확인합니다. 재부팅 후에는 기존 서버 시작 파일을 실행해야 합니다.

[웹 신청 설정과 제한](WEB-REQUESTS.md)을 참고하세요. Chat에서 `@우사기 웹` 또는 새 메뉴의 웹 음악방 링크로 접근합니다. 회사 Wi-Fi에서만 열립니다.

## 서버를 다른 컴퓨터로 이전

1. 새 컴퓨터를 같은 회사 Wi-Fi에 연결하고 [Node.js 공식 LTS](https://nodejs.org/en/download)를 설치합니다. 이 버전의 프로젝트는 Node 24.22.3 이상(24 LTS) 또는 26.13.1 이상(26 LTS)을 요구합니다. 저장소의 `main`을 내려받은 뒤 새 `office-jukebox` 폴더에서 `node --version`을 확인합니다.
2. 기존 컴퓨터에서 서버를 정상 종료합니다. 터미널에서 실행했다면 Ctrl+C를 누릅니다. 백그라운드로 실행했다면 macOS에서 `lsof -nP -iTCP:8787 -sTCP:LISTEN`으로 프로젝트의 Node 프로세스를 확인한 후 해당 PID에만 TERM 신호를 보냅니다. 리스너가 사라졌는지 확인하고, 새 컴퓨터로 이전하는 동안 두 서버를 동시에 실행하지 않습니다.
3. 기존 설정 파일 `config.local.json`과 설정 파일 기준 `data` 폴더의 `state.json`을 새 저장소의 같은 위치에 복사합니다. 설정의 `dataDir`을 바꿨다면 그 경로를 따릅니다. 선택적으로 `state.json.bak`도 보관합니다. 이전 PID가 들어 있는 `server.lock`은 복사 대상에서 빼고, `npm run init`은 건너뜁니다. 설정에는 API 키·관리자 키·TV 연결 정보가 있으므로 접근이 제한된 사내 전달 수단을 사용합니다. TLS가 켜져 있으면 설정의 인증서와 개인키 파일도 필요합니다. 새 IP에서 다른 기기로 관리 화면을 열려면 새 IP 또는 실제 접속 이름에 맞는 인증서를 준비합니다.
4. 새 Mac에서 `networksetup -listallhardwareports`로 실제 Wi-Fi 장치를 확인해 `lan.networkInterface`를 맞춥니다. `lan.advertise: true`, 첫 번째 `lan.hostnames` 값 `office-jukebox.local`, 포트 `8787`을 유지하면 같은 단축 주소를 계속 쓸 수 있습니다. Windows나 Linux에서는 내장 광고의 `lan.advertise`를 `false`로 설정합니다. 다른 기기에서 접속할 때는 새 컴퓨터의 사설 IP를 사용하고, 기존 `.local` 주소와 Chat 웹 바로가기를 유지하려면 회사 네트워크에서 해당 이름을 새 컴퓨터로 해석하도록 구성해야 합니다. 이 프로젝트의 Chat 바로가기는 설정의 첫 번째 유효한 `.local` 이름을 사용합니다.
5. 새 컴퓨터의 저장소에서 `node src/main.js doctor`, `node src/main.js check-google`, `npm start` 순으로 실행합니다. 이 프로젝트에 포함된 기존 Mac 시작 파일에는 원래 컴퓨터 경로가 들어 있으므로 새 컴퓨터에서는 위 명령으로 시작합니다. 재부팅과 절전 이후에도 서버가 필요한 경우 새 컴퓨터에서 전원·절전 설정과 재실행 방법을 확인합니다.
6. 새 컴퓨터에서 `http://127.0.0.1:8787/health`와 `/queue`를 확인하고, 같은 Wi-Fi의 다른 기기에서 공유 주소로 접속합니다. 대기곡 순서와 Google Chat의 `전체 플리`를 확인한 뒤 검색을 시험합니다. 새 Chat 서버가 기존 worker 임대를 넘겨받을 때 잠시 기다릴 수 있습니다. 같은 TV와 설정을 옮겼다면 기존 TV 코드 연결을 먼저 확인하고, 연결이 해제됐을 때만 서버 종료 후 새 컴퓨터에서 `node src/main.js pair-tv`를 실행합니다. 현재 재생이 있으면 서버는 관측을 시도하며, 실제 화면을 확인한 뒤 재시도 여부를 결정합니다.

되돌려야 하면 새 서버를 먼저 종료합니다. 새 컴퓨터에서 신청을 받은 뒤라면 그 서버의 최신 `state.json`을 원래 컴퓨터에 먼저 옮겨 신청을 보존합니다. 각 컴퓨터의 LAN·TLS 설정은 해당 컴퓨터에 맞는 값을 사용합니다.
